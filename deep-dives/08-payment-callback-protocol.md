# Deep dive 8 — The payment callback is a protocol, not a notification

## The problem

Every other inbound message in this system is a *notification*: LINE says something happened, I do the work. A payment callback is different in kind — the provider is running a state machine, and **my HTTP response is the input that advances it**. Answer wrongly and it either retries forever, or stops retrying an event I never processed, leaving a card charged and nothing granted.

Three properties make it hostile in a way ordinary webhooks are not:

- **The same event arrives more than once**, by design. Retry is the provider's correctness mechanism, so duplicates are the normal case.
- **A forged callback is byte-identical to a real one** except for a signature — and the endpoint is public, unauthenticated, and grants paid access.
- **Some failures can never succeed on retry.** An unknown order number will still be unknown in five minutes.

## The shape of the solution

```
ECPay ──POST /payment/ecpay/notify──▶  (public route, outside the auth middleware)
        1  verify signature over the payload        → mismatch: 400, warn, no writes
        2  look up the order by merchant trade no   → unknown: permanent failure
        3  check amount against the order           → mismatch: permanent failure
        4  one transaction:
             lock the order row
             already paid? → done, no second grant
             extend expiry, mark paid, store the raw callback
        5  respond:  "1|OK"  = stop retrying (success *or* permanent failure)
                     500     = transient, please retry
```

The order number is generated by me, not the provider — so the idempotency key exists from the moment the checkout form is built.

## Authenticity replaces identity

Every other route sits behind middleware that verifies a LINE identity token. This one can't: the caller is a server that has never heard of my auth scheme. So it's registered on the bare router, outside the authenticated group, and what would normally come from a session comes from the payload — the signature says *this body came from someone holding the shared secret*, the order row says *whose it is*.

That inverts what trust means here. Normally you authenticate the caller and then believe what they sent; here the caller is anonymous and the payload authenticates itself, so every field that matters is re-checked against state I already hold — the amount is compared against what was recorded at order creation, which was never accepted from the client either (the purchase page posts a plan code; price lives in one table in server code).

## The response code is the control channel

The part that reads as wrong the first time, and is the core of the design: **a permanent failure is acknowledged with success.**

| Situation | Response | Why |
|---|---|---|
| Credited successfully | `1\|OK` | Nothing left to do |
| Database unreachable | `500` | Retry is exactly the right remedy |
| Unknown order / amount mismatch | `1\|OK` + loud log | Never credit, never retry a poisoned event |
| Simulated-payment flag where forbidden | `1\|OK` + loud log | Refuse the grant without inviting a retry loop |

The response answers "should you send this again?", not "did everything go well?". Conflating the two is how one malformed event becomes a retry loop that outlives the bug that caused it — and the price of separating them is that an acknowledged failure has to log loudly enough to alert on, because a human is now the only recovery path.

## Idempotency is a database property, not application logic

Crediting is one transaction: lock the order row, refuse the transition if it's already `paid`, extend the expiry, mark it paid. `paid` is absorbing — `created` and `failed` may both become `paid` (a card retry after a decline is ordinary), nothing leaves it. A duplicate callback finds a paid row, does nothing, returns success, without a single `if` about duplicates in the handler.

Renewal arithmetic lives in the same statement rather than in Go:

```sql
premium_until = GREATEST(COALESCE(premium_until, now()), now()) + make_interval(days => $2)
```

Buying again on day 80 of 90 adds to what's left; buying after a lapse starts from today. Keeping it in SQL means the value can't be computed from a stale read, and the rule exists in exactly one place.

## Signatures are only as strong as byte-identical canonicalization

The scheme is unremarkable — sort the parameters, wrap them in a key and IV, hash — but it's a *canonicalization* protocol wearing a cryptography costume, and the escaping has to reproduce another platform's URL-encoding exactly, including which characters it leaves alone. Go's standard escaper agrees on almost everything and disagrees on `~`: mine left it literal, theirs percent-encoded it. Every signature matched until a value contained a tilde, and then nothing did, with no diagnostic beyond "invalid".

Two habits came out of that:

- **Never hand-compute an expected signature in a test.** The vendor's own generator produced the fixture; the test freezes that vector and checks the algorithm against it. A hand-derived expectation encodes your misunderstanding as the assertion and passes forever.
- **Keep the frozen fixture away from live values.** When the plans were later renamed, the item name inside the signed vector deliberately stayed on the old string — it tests the algorithm, not the catalog. Couple a frozen vector to values that move and every copy change becomes a cryptography change.

## What the design could not save me from

The wiring, not the design, produced the only launch-blocking bug: the callback arrives form-encoded, and that raw body was written straight into a JSON column. Postgres rejected it, the transaction rolled back, the handler returned 500 — and the retry protocol above, working exactly as intended, would have hammered that endpoint forever while every real payment charged a card and granted nothing.

Every unit test passed, because each was written with a hand-built parameter map against a fake store: the seam where a form-encoded body meets a JSON column existed only in wiring no unit test crossed. The fix was one line; the durable change was a rule — **on a money path, a handler-to-real-database integration test is mandatory** — and the test that now exists is written to re-break this bug if it ever returns. Correct protocol reasoning does not survive an incorrect byte at the boundary, and only a test that crosses the real boundary tells you which you have.

## Trade-offs I accepted

- **Permanent failures are silent to the provider.** They're acknowledged, so nothing external signals that a payment went unhandled — the log line is the only alarm, which puts the entire burden on it being worth alerting on.
- **The result page polls.** After redirect it asks for order status every couple of seconds for about half a minute rather than holding a connection open. The authoritative grant is the server-to-server callback, so the page is a convenience for whichever tab happens to be open; when it times out, the push notification still arrives.
- **A simulated-payment flag is honored in development.** The test environment can emit callbacks that were never really paid; accepting them makes the loop testable without a card, and an environment switch keeps it off elsewhere. A deliberate footgun with the safety on.
