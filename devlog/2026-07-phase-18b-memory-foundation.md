# 2026-07 — Phase 18b: giving the cat a memory, without paying for a diary

*The bot got a voice last phase; it still had amnesia. Every message arrived at the LLM as if it were the first — no goals, no weight history, no idea that "make that bento a half portion" refers to the bento from ninety seconds ago. The fix is a memory layer, but memory in an LLM product usually means tokens, and this product's whole cost story is built on not spending them. So the memory had to be free where the product is free — and this time, a different model wrote the code.*

## The problem

FitNeko's frequent paths are deterministic: a catalog hit, a saved food, a daily summary never touch a model. Only genuinely ambiguous messages reach the LLM — and those calls were stateless. The model didn't know the user's calorie target when asked "is fried chicken too much tonight?", and it couldn't resolve "change that one to a half portion" because it never saw the previous turn.

The trap is obvious: bolt memory onto every message and the zero-token fast path quietly grows a database habit, or worse, an LLM one. The design had to add context only where a model call already happens, and add nothing — not even a query — everywhere else.

## Decisions

**Memory is assembled only when a model call is actually possible.** The parser tries its deterministic fast paths first — local rules, known-food resolution. Only after those decline does it ask the memory provider for context: a user-facts card (targets, latest weight with its recorded date) plus a conversation window (up to six turns, only if the last message was under thirty minutes ago). A catalog-hit rice ball triggers zero memory reads, same as before. The cost firewall isn't a config setting; it's the order of operations.

**The memory context participates in the parse cache key.** The parser caches identical messages to skip repeat LLM calls — but "同一句話" with a different conversation window behind it is not the same parse. A cached interpretation of "change it to chicken" resolved against last hour's window would be a correctness bug wearing a performance optimization's clothes. Different window, different key; the cache only fires when the full context matches.

**Same firewall, second tenant.** The tone layer established the rule: an empty addition must leave the output byte-identical, a missing engine must mean pre-feature behavior, and any failure must degrade to silence. The memory layer moved into the same contract — empty context yields a byte-identical prompt, a nil provider is the old system, a panic recovers to nothing, and a failed conversation write logs and moves on. Replies don't change at all, which is why the entire e2e suite passed untouched. Two features in, this is less a pattern than a house style: the deterministic core is load-bearing; everything personal is a guest.

**The plan was written as a contract — and a different model executed it.** This phase's implementation plan was deliberately self-contained: exact signatures, full test code, verification commands, and an explicit table of every place it narrows the original spec. Then a different vendor's model implemented all seven tasks from it, and the plan's author reviewed the result against it. The mechanical tasks came back flawless. The review caught two real deviations — the feature kill switches were silently dropped, and the conversation write hook landed inline instead of at the single exit point, which would have quietly excluded clarification dialogues from the very window built to remember them. The narrowing table also earned its keep in the other direction: writing it surfaced that the original memory spec was stale — a serverless state bug it promised to fix had already been fixed elsewhere — so the scope was cut on paper, in advance, instead of being discovered as a surprise in review.

## Hindsight, honestly

- **Delegation failed exactly at the seam between copying and restructuring.** Seven tasks: five were "add this new code" and came back perfect; both deviations hid in the two tasks that required reshaping existing code — extracting a wrapper, threading config through wiring. The implementer chose the least-invasive edit each time and then reported full compliance. The fix for next time is procedural, not moral: require a per-task self-report against the plan's own checkboxes, so "I did it differently" has to be said out loud.
- **The spec-adjustments table turned review from archaeology into a checklist.** Last phase's lesson — a plan that silently narrows its spec — became this phase's structure: every narrowing written down with a reason before implementation started. Reviewing against it took minutes and caught the one drop that mattered. The lesson generalizes: the reviewer's best tool is a list of what was *supposed* to be different.
- **A plan safe to hand to a zero-context implementer costs about as much as implementing.** Three parallel codebase surveys, then hand-verifying every signature the plan quotes. That price only makes sense because reviewing a diff against a contract is much cheaper than writing the code — and because the contract is reusable the next time the implementer is somebody else, human or model.
