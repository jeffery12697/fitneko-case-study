# 2026-07 — Phase 23: streaks with no streak table

*Retention needed hooks: a 🔥 streak line on every log reply, and milestone achievements that pay out in the same credit currency the coach features spend. Both are the kind of feature that rots a schema — counters that drift, backfill jobs, flags nobody trusts. Phase 23's bet was to store almost nothing: the streak is derived on demand, achievement definitions live in code, and the only new table is a record of who unlocked what, when.*

## The problem

A streak counter sounds like a column. But a stored counter has to be right under backdated logs ("I forgot yesterday"), soft-deleted records, and timezone changes — every one of which turns an increment into a reconciliation problem. Achievements add money to the mix: unlocking pays credits, SQS delivers at-least-once, and records can arrive concurrently, so "exactly one payout per achievement per user" has to survive retries and races. And none of it is allowed to matter more than the log itself: if the achievement layer dies mid-reply, the meal still gets recorded and the reply still gets sent.

## Decisions

**The streak is a query, not a state.** Current streak = take the distinct local-calendar days (user's profile timezone) across diet, workout, and weight records over a bounded lookback window, and walk backwards from today until the first gap. No table, no counter, no backfill. Backfilling yesterday's meal repairs the streak arithmetically — an implicit grace day that rewards coming back after a missed day, and costs nothing to support because nothing was stored. Soft-deleting your only log of a day breaks the streak the same way: the query re-derives, so the data can't disagree with itself. If the rules ever tighten, that's a query change, not a migration.

**Definitions in code, unlocks in the database.** The achievement catalog — conditions, rewards, retirement flags — is Go code, version-controlled and unit-testable. The one new table stores `(user_id, achievement_id, unlocked_at)` with the pair as primary key, and that key is the idempotency lock: unlocking is `INSERT … ON CONFLICT DO NOTHING`, and the credit payout runs only when the insert actually inserted. Payout failure compensates by deleting the unlock row, so the next log retries naturally — the same create-then-compensate pattern the strength-training flow already used, instead of a transaction smeared across packages. Two hard rules guard the future sticker wall: achievement IDs are never reused, and retired definitions are flagged, not deleted — someone's profile still holds that ID.

**One hook, lazy facts, free backfill.** The only trigger is "a record persisted"; every condition evaluates against the database's current state, with the supporting facts (record counts, first-vs-latest weight, goal set) loaded lazily and memoized so unused conditions cost zero queries. Because conditions read accumulated state rather than events, shipping a new achievement later needs no backfill job — existing users unlock it on their next log. The accepted trade: a "goal set" achievement unlocks one record *after* the goal is set, slightly detached from the moment it celebrates.

**Reward pacing did the job of a rate limiter.** The credit economy caps free earnings at 10–15/month, which usually means cap machinery. Here the launch catalog was simply tuned to the cap: an active first month earns about 11 credits across the onboarding set plus the first streak milestone, the 30-day streak lands in month two, and everything is one-shot and lifetime-bounded — so no monthly-cap mechanism was built at all.

## Hindsight, honestly

- **Sequential migration numbers and parallel phases collide by construction.** This phase was developed in a worktree alongside 21a; both claimed the next migration number, and the achievement migrations had to be renumbered after the other branch merged first. With integer-ordered migrations, two concurrent branches *will* fight — the fix is procedural (claim numbers at merge time, not branch time), but it cost a rebase to learn.
- **A "for now" column type became a review-time archaeology dig.** The credit ledger's `source_id` was typed UUID because early sources were UUIDs; achievement IDs are strings, and inserting one would have thrown a runtime type error. Widening to TEXT was safe — but proving it safe meant auditing every consumer of the column. Generic-sounding columns deserve generic types on day one.
- **The degradation philosophy is now a house style, and that's the real asset.** "Record first; the extra layer returns zero and logs on any failure" was designed once for the tone layer, reused for memory, and reused again here — the third tenant made the pattern's value obvious: new features get resilience by moving into the contract instead of designing their own. Naming these patterns early is what makes the third use cheap.
