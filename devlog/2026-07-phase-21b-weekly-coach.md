# 2026-07 — Phase 21b: the weekly coach — numbers from the database, opinions from the model

*Daily logging was solved; reflection wasn't. Users could see any single day, but "how did this week actually go?" required scrolling and squinting. Phase 21b ships a weekly report: a deterministic stats block, an LLM commentary on top, a snapshot table so old weeks are never re-billed, and — for premium users — a Monday-morning push. It's also the first feature where the acceptance bar is explicitly non-deterministic: the commentary must be* insightful*, and no assert statement can check that.*

## The problem

A weekly report is an easy feature to build badly. Let the LLM summarize raw logs and you get three failure modes at once: numbers that drift from the database, cost that grows with how much the user logs, and a bill for re-reading the same week twice. And the push half has a classic distributed-systems trap — SQS delivers at-least-once, and "at least once" is exactly the wrong number of weekly reports to send a paying customer.

The design had to hold three lines simultaneously: every number comes from SQL, every LLM call costs the same regardless of data volume, and every charge maps to fresh analysis actually delivered.

## Decisions

**A numbers firewall, and a rubric where asserts can't reach.** The stats block — per-day calories and protein, days on target, weight delta, workouts, streak — is assembled deterministically and rendered as-is; the LLM sees a compressed weekly aggregate (at most seven per-day rows, so input cost is flat no matter how heavily the user logs) and returns only qualitative output: a headline, commentary, highlights, next-week advice. It is instructed not to restate numbers. This split also split the testing story: the stats side is asserted down to hand-computed samples, while "the commentary has insight" is deliberately accepted via a human-scored rubric eval on fixed sample weeks — a conscious contrast to the previous phase, where every acceptance criterion was mechanically checkable.

**You pay for analysis, not for asking.** Fresh analysis costs 2 credits behind a confirm-before-spend prompt; replaying an existing snapshot is free and writes zero ledger rows; premium skips the gate entirely. Early in the week, when this week has under two logged days, the bot falls back to last week's report — free if snapshotted, billed once if it has to compute. After the deduction, *any* failure refunds — and when the daily refund cap blocks the refund, the bot says so honestly instead of pretending nothing happened. The expensive call sits at the very end of the pipeline: no goal set, snapshot available, or user declines, and the LLM is never invoked.

**The push is a claim, not a check.** The Monday push reuses the entire existing pipeline — an EventBridge Scheduler cron drops one scan message into the existing SQS queue, the existing worker fans out one job per premium user, zero new Lambdas. Idempotency is done as claim-then-push: an atomic `UPDATE … WHERE pushed_at IS NULL` claims the report, and a failed push releases the claim so the retry can take it. The naive order — check the flag, push, then set it — double-sends exactly when SQS redelivers. The claim design got a live validation on launch day: LINE's real API rejected the report card over a flex property the test stub happily accepted, and the released claim meant the fix re-pushed cleanly with no duplicate.

**The contract plan survived a mid-flight model swap.** Like the memory phase, implementation was delegated to a different vendor's model against a self-contained 16-task plan — and this time the implementer ran out of quota partway through, leaving a garbled progress tracker. Recovery was to trust `git`, not the report: verify the working tree against the plan task by task, keep what matched, finish the rest. The contract review earned its keep again, catching a reversal the tests didn't: the resume path deducted credits *before* re-running the guards, so a user could be charged for a report the guards were about to refuse. Money-adjacent ordering is now something the plan states as an invariant, not an implementation detail.

## Hindsight, honestly

- **The test stub validated JSON, not LINE.** The flex stub accepts any well-formed message, so an invalid property sailed through e2e and CI, and only the real API's 400 caught it — on launch day. A schema-validating stub (or a contract test against LINE's published flex schema) would have caught it for free.
- **Output budget is a latency budget in disguise.** The report's structured output plus model reasoning blew past the 20-second LLM timeout in production, quietly degrading every chat-triggered report to the numbers-only fallback. Capping reasoning effort fixed it — but the lesson is that a bigger response needs a latency plan, not just a token plan.
- **Real cost came in at half the estimate — for a structural reason.** The design priced the report off a raw-token guess; the measured number was half that, because per-day aggregation makes input size a constant. Estimating from the data structure, not from vibes about "a week of data", would have priced it right the first time.
