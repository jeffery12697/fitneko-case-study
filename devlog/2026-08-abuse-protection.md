# 2026-08 — Abuse protection: price the worst user before they show up

*The pre-launch checklist said abuse protection had to ship before invite codes went live. Invite codes went live on August 20. This phase is me paying that debt four days late — and discovering, in my own usage data, that the worst-case user was more expensive than the subscription they'd be paying.*

## The problem

By late August the product had everything an abuser wants: a free tier that reaches an LLM, an invite system that mints credits, and a payment tier whose pricing page says "unlimited." The defenses that existed were real but had a specific gap. Text messages had a daily processing ceiling of 100 and a published limit of 7 *logged meals* per day — but the 7-meal budget only counted messages that successfully wrote a food log. Chat, questions, summaries: all of those could reach the LLM without counting against anything except the 100-message flood ceiling. The true worst-case for a free account wasn't 7 LLM calls a day. It was closer to 100.

And a LINE webhook gives you nothing to fingerprint: no source IP, no device ID. Every request arrives from LINE's own servers. Whatever detection exists has to be behavioral.

## Decisions

**Audit the cost with real data before choosing any knob.** Instead of guessing a per-call cost, I priced my own usage table: every text-pipeline LLM call, actual tokens, actual list prices, p50/p95. Two things fell out. First, my original back-of-envelope cost assumption sat between the median and the mean — plausible, but a "worst case" analysis should have been using p95 all along. Second, and more important: the most expensive message type in the system is structurally *two* LLM calls, not one — "what should I eat?" runs an intent classification and then a recommendation generation, and for paying users it skips the credit charge entirely. A PASS user hammering exactly that intent at the proposed fair-use ceiling of 50 calls/day would cost more per month than their subscription. The ceiling shipped at 40, not 50, because of that recalculation. The lesson generalizes: don't price the average call, price the worst *chain* a user can legally trigger.

**A rate guardrail that answers once, then goes quiet.** The webhook now counts messages per user per minute — 30 is the line, far above any human burst — and the trip behavior is deliberately hybrid: the message that crosses the line gets one canned reply ("訊息太多啦！健健貓需要喘口氣，五分鐘後再來喵🐾"), everything after it in the window is dropped silently. Pure silence looks like the bot is broken to a real person who fat-fingered an album upload; a canned reply to every message hands a script free output. One reply per window caps both costs. A review pass added the cooldown: a fixed window quietly *refills every minute*, so a sustained flood was getting a fresh 30-message allowance per minute — the trip now opens a five-minute cooldown. And the whole gate fails open: if the counter's database call errors, the message goes through with a warning log. A broken guardrail must degrade to "no protection," never to "no service."

**Cap LLM calls, not messages.** The new daily quota counts the thing that costs money — actual LLM parse calls — not messages. Keyword chips, cached repeats, and everything else the deterministic layers absorb stay free, so the cap doesn't punish normal heavy use of the cheap paths. Free accounts get 10/day (the published 7-logs promise keeps its own counter, untouched). PASS keeps "unlimited" on the pricing page — because for logging it genuinely is — but the terms now carry a fair-use clause, and the implementation carries the 40/day ceiling. The exhaustion message for a paying user deliberately never says "abuse": someone hitting 40 real LLM calls in a day might just be an extremely enthusiastic human, and they get "明天見喵," not an accusation.

**Detection is a digest section, not an alarm.** Multi-account farming can't be fingerprinted, only noticed. Five behavioral rules — today's rate-limit trippers, an anomalous new-account count, invite-reward concentration, brand-new accounts that max their LLM quota on day one, PASS accounts hitting the fair-use ceiling — render as a "⚠ anomalies" section in the existing daily ops digest, and the whole section vanishes on quiet days. No real-time alerts, no auto-blocking: at this user count the next morning is fast enough, immature rules are noisy, and the kill switch (the admin panel's block button) stays a human decision.

**The follow-up: monthly quotas became weekly.** Voice and photo quotas for PASS moved from monthly buckets to 50/week and 40/week — a month is a long time to be told "you've used it all," and a weekly bucket keyed to the user's local Monday resets the frustration clock. Same atomic counter, new bucket key, and the deployment itself was the migration: everyone's count restarted, an error in the user's favor.

## Hindsight, honestly

- **This was the umbrella that had to be up before launch, full stop.** Without it, an automated bot attack could take the service down or send the bill through the roof — for a product that pays per LLM call, abuse protection isn't hardening, it's a launch prerequisite.
