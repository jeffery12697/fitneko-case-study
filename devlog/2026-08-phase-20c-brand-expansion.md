# 2026-08 — Phase 20c (part 2): three more tea chains, and every one broke an assumption

*The drink catalog launched with three brands and a model tuned to them. This wave adds three of Taiwan's biggest chains — 麻古 (52 drinks), 清心福全 (98), 得正 (30) — doubling the catalog to 648 size-level entries across six brands. The plan said "data entry." The reality was a series of model amendments, because every new chain violated an assumption that had quietly become code. Shipped as PRs #152 and #155–#159, plus a search fix in #153.*

## The problem

The decomposed drink model worked because the first three brands happened to agree on things no spec ever promised: everyone sells an M cup, everyone uses the standard sugar ladder, everyone's official table includes a bare-tea row you can derive from, and one shared topping list is close enough. Each new brand falsified one of these — and because the engine is an accelerator that silently falls through to the generic estimate rather than erroring, a falsified assumption doesn't crash anything. It just quietly turns curated data back into guesses. The work of this wave was hunting those silent degradations down and turning each hardcoded assumption into per-brand data.

## Decisions

**Brand conventions become per-brand data, one break at a time.** 麻古 sells large cups only, so the hardcoded "default cup size is M" meant every 麻古 order without an explicit size missed the catalog entirely — the default is now derived per brand from what it actually sells. 清心福全 abolished full sugar under the government's sugar-reduction policy, so its published maximum is 少糖 and the shared sugar ladder misreads every order; the ladder became brand-scopable data, rescaled so the brand's own top rung maps to 1.0. And brands were matched verbatim: the parser hands over whatever the user typed, so 「清心」 could never match rows stored as 「清心福全」 — a canonical-brand lookup with alias rows now runs before anything else. None of these are special cases in code; they're rows, with the old behavior as the shared default.

**Sugar split into a fixed part and an adjustable part.** For drinks whose official figure bakes in a syrup-soaked topping, the topping's sugar was being scaled down with the sweetness level — but ordering your pearl milk tea sugar-free doesn't desweeten the pearls. The distortion was visible: a sugar-free coconut-jelly milk tea computed *lighter than the same milk tea without the jelly*. Each base now carries the grams of sugar that don't respond to the sugar dial, and only the remainder scales. The fixed part is derived from the brand's own table — subtract the bare-tea row from the topped row, same-table arithmetic rather than guesswork — and where several independent subtractions exist they agree to within a tenth of a gram, which is the derivation validating itself. Two properties were non-negotiable: every row still reproduces the brand's published full-sugar figure exactly (the audit trail survives), and where no defensible subtraction exists the field stays empty — filling it from the generic topping table would be estimation wearing arithmetic's clothes. 181 rows across two brands got the split.

**Toppings share identity but not facts.** One brand-agnostic topping table produced three visible lies: the MINI app offered toppings a shop doesn't sell, calories came from a canonical value when the brand publishes its own (得正's pearls: officially 191 kcal, we said 120), and toppings never appeared in the logged item's name. The fix is an overlay: the shared table remains the vocabulary and the default numbers, and a per-brand table asserts what's actually sold, what it costs at each cup size, and what the shop calls it — any field left empty falls back to shared. Ordering a topping the brand doesn't sell still computes (accelerator, never a gate) but flags the entry for review. The subtlest part was carrying brand and size through the server-side recompute path, because the 22c contract — the frontend previews, the backend is authoritative — silently breaks the moment the authority knows less about the drink than the preview did.

**A published number that contradicts itself doesn't ship.** 得正's poster lists one drink at 378 kcal with 141 g of sugar — the sugar alone would be 564 kcal, so the two numbers cannot both be true. Rather than guess which digit is wrong, the drink is excluded, and a test asserts its absence so it can't reappear unnoticed. The same discipline runs through the wave: bottle and sharing-jug sizes aren't seeded because the size normalizer has no code for them and unreachable rows would masquerade as coverage; a misprinted product name on an official poster is seeded under the correct spelling with the misprint kept as an alias, so either resolves.

**Storage keys stop leaking to the surface.** Two front-door fixes rounded it out. Search matched brand and product name as separate fields, so typing the glued string 「可不可熟成紅茶」 — the way people actually write it — found nothing; the search now also matches against the concatenated brand-plus-name. And internal source tokens (the health-ministry tag, the convenience-store tag) had been showing up on cards and in search; a brand registry now translates every token to a display name before it reaches a screen, and the raw keys are treated as what they are — storage, not copy.

## Hindsight, honestly

- **The design that made the engine safe made the gaps invisible.** "Accelerator, never a gate" was the right call in part 1, and it's still right — but every assumption this wave falsified had been failing *silently* for exactly that reason. No error when every sizeless 麻古 order missed the catalog; no error when 「清心」 never matched anything. The correct behavior and the broken behavior looked identical from the outside. The lesson isn't to remove the fallback — it's that a fallback taken for a *curated* brand is a signal worth counting, and nothing was counting it. Falling through should be fine; falling through invisibly is how curated data quietly rots back into guesses.
- **Writing the procedure down as a skill was the part-1 bet, and this wave is where it paid interest.** The sugar-split PR updated the curation skill in the same commit — the derivation steps, the no-bare-row fallback order, three new mistakes-to-avoid — and the very next brand curated (得正, the same day) hit the same class of problem and handled it correctly on the first pass, using the brand's own published topping sugars instead of re-deriving. A lesson that lives only in a merged PR is a lesson the next session re-learns; a lesson that lands in the procedure file is one it can't skip.
