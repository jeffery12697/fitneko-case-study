# 2026-08 — Naming the paywall, then building the wall it implies

*Selling access forces two questions a free product never has to answer: what is this thing called, and what exactly is on the other side of it. This phase renamed the paid tier, rebuilt the purchase page around a comparison table, and — the real work — implemented the five quota gates that make the free tier a defined product instead of an unbounded one. Shipped as PR #177.*

## The problem

The paid tier had been called 通行證 — "pass," in the access-control sense, the word a turnstile would use. It was accurate and it was wrong: it names the *barrier* rather than the *value*, in a product whose entire voice is a cat that encourages you. Worse, the purchase page listed three durations and three prices and said nothing about what changed if you bought one, because at that point nothing did change: the free tier had no limits, so "free vs paid" had no honest table to render.

So the naming problem and the product problem turned out to be one problem. Deciding what to call the tier meant deciding what it contained, and deciding what it contained meant capping the free tier — which meant the free tier needed a shape a user could hold in their head.

## Decisions

**The SKU names carry the mental model.** The tier became 教練 PASS ("coach pass"), and the three products became 月卡 / 季卡 / 年卡 — month card, season card, year card — with the day counts demoted to a subtitle. Taiwanese users already own this frame: gym cards, mobile-game monthly cards, all one-off purchases that expire, none of them subscriptions. "Buy a season" also reads as a *plan* in a way "buy 90 days" reads as arithmetic, which matters when the product's own claim is that a fat-loss cycle takes about three months. The internal plan codes were deliberately left alone — this is a copy change from the database's point of view, and renaming enum values that a payment provider's item names and a CHECK constraint both depend on would have been risk with no benefit.

**Quotas are counted in the unit the user can verify, not the unit that costs money.** The free text limit is seven *successful records per day*. The honest cost driver is LLM calls, but that number is unpredictable from the outside — a cache hit or a catalog match costs nothing, so a user counting their own messages would find the meter disagreeing with them. Counting records makes the promise checkable: seven logged meals is seven logged meals. The gate and the meter therefore sit at different points in the pipeline — the meter increments only after a row is written, and the gate sits deeper, immediately before the LLM is actually invoked.

**The overage behaviour is soft, and the pipeline architecture is what makes that free.** The parsing funnel already resolved rules, saved foods and catalog hits before ever reaching the model. Putting the budget check *after* those layers means an over-quota user can still log 「滷肉飯」 — the catalog knows it, it costs nothing, so nothing blocks it — while a genuinely novel meal gets the upsell. This preserves the product's oldest promise ("recording is never blocked") without a single special case: the cheap paths simply never pass through the gate. It is the clearest payoff yet from a funnel built for cost reasons two months earlier.

**Voice and photo moved behind the pass, and the credit economy became their overflow.** Voice previously shared the text budget and photos had three free recognitions a day; both are now pass features with monthly allowances, and the free daily photo pool was removed outright. The interesting part is what happens when a paying user exhausts a monthly allowance: rather than a hard stop, they fall into the pre-existing credit-confirmation flow — spend an earned credit to continue. That was already the stated role of the credit currency ("what a paying user spends after their allowance runs out") and it needed no new interface, just the two paths meeting.

**One table, one atomic statement, and the day boundary the user lives in.** All periodic usage lives in a single table keyed by user, feature and period start, and the check-and-increment is one `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE used < limit RETURNING` — no read-then-write, so a double-tap cannot exceed the cap. Periods are computed in the user's own timezone, because the existing credit system resets on UTC midnight, which in Taiwan is 8am — a "seven per day" promise that resets over breakfast is a broken promise, and reusing that mechanism would have inherited the bug. When the quota table itself errors, the text gate fails *open*: a broken meter must never block recording.

**The purchase page answers the question it used to dodge.** The rebuilt page is a comparison table — every row now has a real difference on both sides, which is only true because the free tier finally has limits — sitting under three ticket-shaped cards with punched notches, a per-day price breakdown, and a savings badge. A dashed reassurance strip states plainly that free features are not taken away when a pass expires. The mascot got a purpose-drawn pose for it (a conductor holding out a ticket) rather than borrowing a dashboard illustration, and the copy never mentions the credit currency — that economy is deliberately invisible on the page where money changes hands.

## What the process caught

Fifteen tasks, each implemented by a fresh agent and reviewed by another against the spec. The reviews earned their cost on the things a single pass would have shipped: a monthly voice allowance that was decremented but never refunded when the download, the file-length check or the transcriber failed; credits taken for a voice retry with no refund path at all; a local-development entry point that constructed its own copy of the pipeline and had been left without the new gate, so the feature would have been invisible in exactly the environment used to develop it. None of those are subtle once named, and none of them were in the plan.

The remaining gap was found by CI, after merge, and it was mine: the plan's local verification steps covered the Go and web unit suites but not the two end-to-end suites, which encoded the *old* behaviour — a free user's first photo being recognised for free. The suites were right to fail. Updating them to assert the new confirmation flow made them better tests than they were before.

## Hindsight, honestly

- **Naming the tier was product work disguised as copy work, and doing it first was lucky rather than clever.** The rename forced the question "what is actually on the other side of this?" before any gate existed, which is the order that produced a comparison table worth rendering. Had the gates been built first, the table would have been designed around whatever the limits happened to be.
- **The cheap-path funnel keeps paying dividends it wasn't built for.** It was built to reduce token spend; it turned out to be the mechanism that makes a free-tier cap humane, because the gate can sit behind the free layers instead of in front of the feature. Architecture chosen for cost reasons ended up deciding a product-ethics question.
- **Reviewing every task doubled the agent cost and paid for itself in currency bugs.** Three of the findings involved real money or real user-visible blocking. The uncomfortable part is that the plan — which I wrote — was the source of two of them by omission, so the review was catching my design gaps, not implementation sloppiness.
