# 2026-09 — Phase 18c: three cats, one arbiter, and an eval that had to learn what production actually says

*Phase 18b gave the cat a voice — one voice, chosen by rule, appended after the numbers. This phase lets the user pick the cat: gentle, coach, or tsundere, plus a "numbers only" switch. The hard part was not writing three sets of copy. It was making an LLM-generated line and a hand-written line come out of the same door, under the same rules, and proving it with an eval that judges what the user sees rather than what the model said.*

## The problem

The tone layer worked, but it had one personality and every user got it. Retention is the goal of this product's companion features, and companionship is personal: some people want to be teased about the 1 a.m. fried chicken, some want a coach who only states the gap, some want the cat to shut up and show numbers. The July spec already named the three gears. Two months of shipping in between changed the shape of the job: a memory layer now feeds every LLM call, a text-parse cache can replay a joke verbatim, the weekly report and daily advice have their own prompts that call themselves the cat, and a settings page exists where a toggle naturally belongs.

There was also a cost constraint I refused to move. Most replies never touch a model — that is the whole economics of the parsing funnel — so personality could not become an LLM feature. It had to work identically whether the reply came from a catalog hit, a cache hit, or a real parse.

## Decisions

**One arbiter; the LLM is a candidate, not an author.** Every reply still asks the deterministic tone engine for its one line. When the parse did go through the model, the model may propose a `tone_line` in the same call — zero extra requests — and that proposal enters the engine as a *candidate*. The engine decides: quiet mode wins, then the candidate has to pass four gates (single line, length ceiling, a loan-word blocklist, no digits), then the persona's hand-written pool, then the default pool, then silence. The service layer never inspects the candidate and the engine never knows where it came from. Two paths, one voice, and the numeric block stays byte-identical to before — the 18b firewall, unchanged.

**The copy pool is the few-shot set.** I did not write a prompt style guide. The hand-written pool that already drives deterministic replies is sampled — ten lines per call — into the `[Persona]` block the model sees, alongside a short character sheet and the shared safety rules. Editing one JSON file changes both the canned lines and the model's voice, and the lint that checks the pool (length, punctuation, blocklist, "the weight surface only encourages") is therefore also the few-shot lint. One correction came out of review: mode-switch confirmations ("coach mode on") were being sampled as examples of how the cat talks while logging a meal, and had to be excluded.

**The persona block lives in the user turn, and never in the cache key.** Per-user state in the system prompt would have split the provider's prompt cache three ways; the block goes after the memory context in the user segment instead. The text-parse LRU includes the persona *gear* — switching gears must re-parse so the voice actually changes — but not the block itself, because the few-shot is sampled fresh each call and would make the cache miss forever. And the model's `tone_line` is attached only *after* the cache write, so a cache hit never replays the same tease.

**"Quiet cat" is a switch, not a fourth persona.** The original ask listed four personalities; the fourth was "just the numbers." That is not a voice — it is the engine returning nothing — so it became a boolean the engine checks first. Zero copy to write, zero prompt to maintain, and the user's chosen persona survives underneath it.

**Switching is a pre-parse keyword rule with a short-message guard.** "兇一點" is a settings change, not a food log, so it is caught before parsing and costs nothing. The guard is length: a Chinese message has to be eight characters or fewer, English twenty-four, so a sentence that merely contains the phrase — "the coach was fierce, gave no quarter" — is not swallowed. The confirmation is spoken in the *new* voice, which is the one moment in the feature that is deliberately shareable. Review caught one substring collision (an English "end quiet mode" matched "quiet mode" first and turned quiet on); more-specific markers now sort first.

**Safety is enforced where the model cannot argue with it.** Three rules moved from prompt text into code during this phase, each after the eval showed the prompt alone was not enough. The weight surface ignores candidates outright — a weigh-in gets encouragement from the pool, whatever the model wrote. A deterministic detector for frustration ("又失敗了", "so sad") and for self-referential body talk ("變胖了", "臉好圓") drops the candidate and answers in the gentle voice for that one reply, without touching the user's saved persona. And when the user disparages a brand or their own body first, the prompt now says the cat does not pick up the thread — the eval had shown the tsundere gear happily agreeing.

## What the eval taught me

The acceptance line in the spec was "zero violations across the mine-field scenarios" — body and appearance, regional stereotypes, brand disparagement, and "pure encouragement when the user is down." Sixty-three scenario × persona pairs, a live model, an LLM judge. It took six runs.

Run one found two real problems and four judge misreads. Run two found that the eval was judging the *raw* candidate, including lines production would never show — a weigh-in candidate the engine discards, an intent that never threads a candidate at all. The fix was to make the eval compute the delivered line the way production does: apply the frustration backstop, run the engine, judge only what survives. Runs three to five each surfaced one or two borderline readings, almost all about whether a line was *purely* encouraging — the tsundere gear opening with 「哼」 before comforting someone, a coach line that "states the gap" — and one real one: the body-talk case above.

Both the model and the judge are stochastic, so a hard zero on a fuzzy category is a target that moves every run. My call, in the end, was two tiers: body, region and brand are zero-tolerance and fail the test; "pure encouragement" is collected for human review and does not. Run six passed clean under those rules, with the deterministic backstop firing exactly on the fifteen pairs it was designed for.

## Hindsight, honestly

- **Write the eval to judge what ships, from the first run.** Two of the six eval rounds were spent discovering that the harness scored lines the engine would never deliver. The eval should have mirrored the production path — backstop, engine, weight rule — before it ever judged a single sentence.
- **Keyword lists need a food-log-shaped negative test suite, not just a positive one.** Every safety keyword list I added ("好累", "i'm done", "好肥") shipped with a plausible false positive on an ordinary meal log, and each was caught in review, not when I wrote it. The negative cases — brand names, food descriptions, exercise fatigue — are the ones that matter for a detector that sits in front of every message.
- **A stochastic judge needs its acceptance criteria written down before the first run.** "Zero violations" sounded rigorous; against a judge that reads 「哼」 differently each time it became a loop. Deciding up front which categories are hard gates and which are review queues would have saved three runs.
